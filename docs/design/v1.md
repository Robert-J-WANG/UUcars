# UUcars Marketplace V1 Design

## Purpose

Build the backend MVP for a consumer-to-consumer used-car marketplace, covering
the journey from account creation and vehicle listing to moderation and purchase.
The API should provide clear business rules, testable responsibilities and a
repeatable local runtime.

## Scope

- Registration, password sign-in and current-user profile management.
- Seller-owned vehicle drafts, image URLs, submission and Admin moderation.
- Public vehicle browsing, filtering, pagination and access-controlled details.
- User favourites, purchase creation, cancellation and buyer/seller order views.
- Service tests, SQL Server integration tests, Docker Compose and CI.

V1 is an API-only release. File upload, email delivery, order completion,
reviews, a browser frontend and cloud hosting are outside its scope.

## Key design decisions

### Application and data structure

Use Controller–Service–Repository separation with ASP.NET Core, EF Core and
SQL Server. Controllers handle HTTP concerns, Services enforce business rules,
and Repositories own database access. DTOs keep persistence entities separate
from the public API contract.

Users, Cars, CarImages, Favorites and Orders form the core model. Foreign keys,
unique email addresses and a composite favourite key protect relationships and
prevent duplicate records. EF Core migrations provide a reproducible schema.

### Identity and access

Hash passwords with ASP.NET Core PasswordHasher and validate JWT access tokens
on protected requests. Derive ownership from authenticated claims, and reserve
moderation operations for Admin users. Public registration cannot assign roles.

Only published vehicles are publicly visible. Sellers can view their own
non-public listings and edit drafts; Admin users can inspect listings for
moderation. Apply these checks in the API for every relevant operation.

### Listing and purchase lifecycle

Vehicles move from draft to pending review and then to published after approval.
Rejection returns a listing to draft, while removal uses a deleted state to
preserve historical relationships.

Purchasing a published vehicle creates a pending order and marks the vehicle
sold. Cancelling that order restores the listing to published. Store the seller
and price on the order to preserve the purchase snapshot, and reject attempts
to buy one's own vehicle.

### API reliability and operation

Use consistent response and pagination models, meaningful HTTP status codes and
central exception handling. Log unexpected failures with Serilog without
exposing internal details to clients.

Docker Compose runs the API with SQL Server. Environment configuration supplies
connection settings and signing keys without embedding secrets in source code
or images.

## Delivery phases

| Phase | Outcome |
|---|---|
| Foundation | Project structure, configuration, logging, database model, migrations and Admin seed |
| Accounts | Registration, password security, JWT validation and profile management |
| Marketplace | Vehicle drafting, submission, discovery, favourites and purchase management |
| Moderation | Admin approval, rejection, pending queue and listing removal |
| Delivery | Business-rule tests, SQL Server integration tests, Docker runtime and CI |

## Validation and acceptance

Use xUnit service tests for business rules and WebApplicationFactory with
Testcontainers for the real HTTP, authentication, EF Core and SQL Server path.
Validate container startup and the build/test pipeline separately.

Acceptance requires:

- the database can be created from migrations;
- users can register, sign in and manage only their own resources;
- listings follow the moderation lifecycle and public queries exclude private states;
- purchase and cancellation keep vehicle and order states consistent;
- unauthorised requests, duplicate resources and invalid transitions are rejected;
- Docker Compose and CI provide reproducible execution without committed secrets.
