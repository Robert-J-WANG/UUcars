# UUcars Marketplace V3 Design

## Purpose

Strengthen the full-stack marketplace through measured performance improvements,
safer sessions and concurrent operations, resilient interactions, real-time
notifications and reliable production delivery. Keep the application
understandable within its existing architecture.

## Scope

- Query optimisation, Redis caching, rate limiting and background jobs.
- Refresh-token rotation, concurrency protection, security headers and Admin auditing.
- Multi-image workflows, draft recovery, optimistic favourites and improved search.
- Frontend component tests and real end-to-end journeys.
- Persistent notifications, Admin analytics and Google sign-in.
- Runtime upgrades, gated CI/CD, frontend performance and production readiness.

Retain the single API and React application. Infrastructure and optimisation
changes must address demonstrated needs within this deployment model.

## Key design decisions

### Read performance and background work

Match database indexes and projections to actual listing, favourite and order
queries. Use Redis cache-aside for repeated reads, with query-specific keys,
intentional invalidation and database fallback when the cache is unavailable.

Use Hangfire with SQL Server storage for email jobs and token cleanup. Workers
run with the API and pause when its container scales to zero; cleanup timing
does not replace token-expiry checks during authentication. Application Insights
and Serilog provide request telemetry and operational logs.

### Session and transaction safety

Keep short-lived access tokens in frontend memory and rotating refresh tokens
in HttpOnly cookies backed by revocable database records. Restore sessions
through refresh and revoke them on logout. Apply workload-specific rate limits,
JWT validation and response security headers at the API boundary.

Use SQL Server rowversion on vehicles to detect competing moderation or
purchase updates and return a clear conflict response. Persist sensitive Admin
actions in an audit trail.

Validate Google ID tokens on the server, resolve external identities to local
users and reuse the existing session system. A unique provider-subject
association prevents duplicate identity links; verified email supports linking
an existing local account.

### Recoverable frontend interactions

Support batch image upload, per-image retry and ordering, with ownership and
image-set validation in the API. Save serialisable draft fields locally and
provide a recoverable fallback for rendering failures.

Optimistic favourites retain rollback state and revalidate after requests.
Debounced search and year filters remain synchronised with the URL. Measure
production bundles and loading behaviour before applying route splitting or
image-priority changes.

### Notifications and administration

Persist notifications before SignalR delivery, using authenticated user groups
for online connections and REST queries for unread history. Delivery failure
must not undo a successful marketplace operation.

Aggregate Admin statistics in SQL, define reporting windows in UTC and fill
missing dates in the Service layer. Briefly cache the result and present
metrics, trends, brand distribution and paginated audit records.

### Verified production delivery

Align local, Docker and CI runtimes. Run backend, frontend and real Playwright
checks before merging a release from develop to main. CD builds both artefacts
from the same successful main commit, deploys the API by immutable image digest
and verifies the frontend release identifier.

Run the API as a non-root user with a writable log directory, and provide
sensitive runtime values through Container Apps Secret references. Protect the
built-in Hangfire Dashboard with the Admin role and a path-limited HttpOnly
access-token cookie. Production acceptance includes telemetry and worker recovery.

## Delivery phases

| Phase | Outcome |
|---|---|
| Performance and security | Query improvements, caching, rate limits, background jobs, session renewal, concurrency and audit records |
| Interaction reliability | Image management, draft recovery, optimistic favourites and URL-based search |
| Automated journeys | Component tests and repeatable browser flows with isolated data and failure diagnostics |
| Real-time administration | Persistent notifications, live delivery and cached Admin analytics |
| Identity and delivery | Google sign-in, aligned runtimes and CI-gated Azure releases |
| Production acceptance | Measured loading improvements, container permissions, managed secrets and operational verification |

## Validation and acceptance

Combine business-rule tests, SQL Server integration tests, component tests and
Playwright journeys. Exercise deployment and operational boundaries with
container checks, browser verification and read-only production smoke checks.
Compare performance under consistent measurement conditions.

Acceptance requires:

- query and loading improvements have measurable evidence;
- cache failures preserve database-backed access and jobs recover with the API;
- session renewal, identity linking, ownership and concurrent updates remain safe;
- failed frontend operations recover without leaving misleading state;
- notifications persist independently of live delivery and analytics follow defined UTC rules;
- CI runs the real application journeys and retains useful failure diagnostics;
- Admin Dashboard access, non-root execution, secret references and telemetry work in production;
- the deployed frontend and API correspond to the same verified release commit.
